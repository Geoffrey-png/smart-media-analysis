## 二、会议背景

随着新闻资讯、短视频、图文内容等传媒数据快速增长，传统人工管理内容和简单列表展示方式已经无法满足用户个性化获取信息、平台内容运营分析和后台管理的需求。

本项目计划搭建一个“智能传媒内容分析与推荐系统”，通过新闻内容采集、内容智能分析、用户行为记录、用户画像构建和推荐算法，实现内容管理、内容分析、用户个性化推荐和管理员后台管理等能力。

本次会议主要围绕系统建设目标、核心用户角色、主要功能模块、技术路线和初步开发范围进行讨论，为后续原型设计、数据库设计和编码实现提供依据。

## 三、项目建设目标

会议初步确认，本系统需要达到以下目标：

1. 建立一个完整的智能传媒内容管理与推荐平台。
2. 支持从新闻源采集真实新闻内容，减少系统内容完全依赖模拟数据的问题。
3. 支持用户浏览、点赞、收藏等行为记录，并根据行为动态更新用户画像。
4. 支持基于用户画像、内容标签、内容热度和内容质量的个性化推荐。
5. 支持内容智能分析，包括摘要、关键词、分类、情感和敏感词识别。
6. 支持内容审核流程，保证内容发布安全。
7. 建立真正可用的管理员后台，支持用户管理、角色权限、账号状态管理和操作日志审计。
8. 前端页面需要更像“分析网站/数据平台”，而不是普通后台管理模板。

## 四、用户角色初步定义

会议讨论后，系统暂定包含以下角色：

| 角色 | 权限说明 |
|---|---|
| 管理员 admin | 拥有系统最高权限，可管理用户、角色、内容、审核、新闻采集、操作日志和系统统计 |
| 编辑 editor | 可进行内容新增、编辑、新闻采集、内容分析和推荐分析查看 |
| 审核员 auditor | 可进行内容审核，查看行为日志、推荐效果和部分统计数据 |
| 普通用户 viewer | 可浏览内容、点赞内容、触发行为记录、查看个人推荐和个人画像 |

会议强调：

- 前端隐藏菜单不能代替权限控制。
- 后端接口必须进行真实权限校验。
- 管理员后台必须是真实功能，而不是静态展示页面。

## 五、核心功能需求

### 5.1 登录认证与权限管理

初步需求：

- 用户可通过账号密码登录系统。
- 登录后返回 Token，用于后续接口认证。
- 系统根据用户角色展示不同菜单。
- 后端接口根据角色限制访问权限。
- 管理员可修改用户角色。
- 管理员可禁用或启用用户账号。
- 被禁用账号不能登录，也不能继续访问受保护接口。

### 5.2 管理员后台

管理员后台需要作为系统管理入口，提供以下能力：

- 系统指标总览。
- 用户数量统计。
- 正常账号 / 禁用账号统计。
- 内容总数统计。
- 待审核内容数量统计。
- 用户行为日志数量统计。
- 操作审计日志数量统计。
- 角色分布统计。
- 内容状态分布统计。
- 新闻来源统计。
- 后台操作日志查询。

管理员后台应重点体现“系统运营分析”和“权限管理”能力。

### 5.3 用户管理

管理员需要可以：

- 查看用户列表。
- 按用户名或昵称搜索用户。
- 按角色筛选用户。
- 按账号状态筛选用户。
- 新增用户。
- 编辑用户基本信息。
- 修改用户角色。
- 禁用 / 启用用户。
- 删除用户。
- 查看用户画像。

约束说明：

- 管理员不能禁用当前登录的自己。
- 管理员不能把自己的角色降级，避免系统无管理员可用。

### 5.4 新闻采集

系统需要支持真实新闻内容采集，初步方案为 RSS 新闻源采集。

需求包括：

- 提供内置新闻源列表。
- 支持用户输入自定义 RSS 地址。
- 支持采集新闻标题、摘要、正文简要信息、发布时间、来源和原文链接。
- 采集后的新闻进入内容资产库。
- 新闻采集操作需要记录到操作日志。
- 采集功能仅允许管理员和编辑使用。

### 5.5 内容管理

内容管理模块需要支持：

- 内容列表查看。
- 内容详情查看。
- 新增内容。
- 编辑内容。
- 删除内容。
- 内容封面或附件上传。
- 内容来源链接展示。
- 内容状态管理。

内容字段初步包括：标题、摘要、正文、作者、分类、标签、来源名称、来源链接、内容类型、发布时间、浏览数、点赞数、收藏数、评论数、热度分、质量分、情感倾向、审核状态。

### 5.6 内容智能分析

系统需要对内容进行演示级智能分析，暂定包括：

- 自动摘要生成。
- 关键词提取。
- 内容分类识别。
- 情感倾向判断。
- 敏感词识别。
- 内容热度分计算。
- 内容质量分计算。
- 相似内容推荐。

会议说明：当前阶段以规则算法和轻量 NLP 方法为主，后续可扩展为真实大模型接口或专业 NLP 模型。

### 5.7 内容审核

内容审核模块需要支持：

- 查看待审核内容。
- 查看敏感词命中结果。
- 审核通过。
- 审核拒绝。
- 内容下架。
- 填写审核意见。
- 记录审核人和审核时间。

权限要求：管理员和审核员可以进行审核，编辑不能直接审核发布敏感内容。

### 5.8 用户行为记录

系统需要记录用户与内容的交互行为，作为用户画像和推荐算法的数据基础。

| 行为 | 说明 |
|---|---|
| view | 浏览内容 |
| like | 点赞内容 |
| favorite | 收藏内容 |
| comment | 评论内容 |
| share | 分享内容 |
| dislike | 不喜欢内容 |

行为记录需要影响：内容浏览数、内容点赞数、用户活跃度、用户兴趣标签权重、用户负向兴趣标签和后续推荐结果。

### 5.9 用户画像

用户画像需要根据用户行为动态更新，初步包含：

- 用户基础信息。
- 兴趣标签权重。
- 负向兴趣标签。
- 分类偏好分布。
- 行为类型统计。
- 最近浏览/互动内容。
- 活跃分。
- 最近活跃时间。

会议确认，用户画像不能完全静态填写，必须由用户行为驱动更新。

### 5.10 个性化推荐

推荐模块需要支持：

- 基于用户画像的个性化推荐。
- 基于内容标签和分类的相似推荐。
- 基于热度和质量分的热门推荐。
- 混合推荐。
- 已浏览内容去重。
- 负反馈降权。
- 推荐点击记录。
- 推荐效果分析。

推荐排序因素初步包括：用户兴趣标签匹配度、内容分类匹配度、内容热度、内容质量分、内容新鲜度、用户负反馈、用户是否已经浏览过。

### 5.11 数据统计与可视化

系统需要提供数据分析能力，包括：

- 内容数量统计。
- 用户数量统计。
- 用户行为趋势。
- 热门内容排行。
- 推荐曝光量。
- 推荐点击量。
- CTR 点击率。
- 内容分类分布。
- 用户活跃度排行。

前端展示应尽量使用图表、指标卡和分析型布局，突出“传媒内容分析平台”的特点。

### 5.12 文件上传

系统支持上传内容相关文件，例如封面图或附件。

要求：

- 文件存储在项目目录内。
- 上传接口需要权限控制。
- 管理员和编辑可以上传。

## 六、非功能需求

### 6.1 易用性

- 页面结构清晰。
- 功能入口明确。
- 管理员、编辑、审核员、普通用户看到的菜单应不同。
- 前端风格应偏数据分析平台，而不是传统后台表格系统。

### 6.2 安全性

- 所有重要接口必须登录后访问。
- 管理员接口必须限制管理员角色访问。
- 操作日志需要记录关键后台操作。
- 禁用账号后应立即无法继续使用系统。

### 6.3 可维护性

- 后端采用 API、Service、Model 分层结构。
- 前端采用 views、api、router、store 分层结构。
- 数据库结构需要便于后续扩展。

### 6.4 部署与环境要求

- Python 虚拟环境放在项目目录内。
- SQLite 数据库放在项目目录内。
- 前端依赖 `node_modules` 放在项目目录内。
- pip / npm 缓存放在项目目录内。
- 提供启动脚本和 README 说明。

## 十、会议讨论结论

1. 项目定位为智能传媒内容分析与推荐系统，重点不是普通 CRUD 后台，而是内容分析、用户画像和推荐能力。
2. 系统必须有真实新闻采集能力，避免所有内容都由系统编造。
3. 用户行为必须能够驱动用户画像变化，并进一步影响推荐结果。
4. 管理员后台必须具备真实管理能力，包括角色权限、账号状态、用户管理和操作日志。
5. 前端视觉风格需要向数据分析平台靠拢，减少传统后台管理系统的感觉。
6. 后端权限控制必须真实有效，不能只依赖前端菜单隐藏。
7. 第一阶段以可运行、可演示、功能闭环为主，算法可以先使用规则和轻量模型实现。
8. 后续可继续扩展更真实的 NLP 模型、大模型分析、推荐实验和多数据源采集能力。

## 十一、待确认问题

1. 新闻源是否固定，还是需要管理员后台维护新闻源。
2. 是否需要支持定时自动采集新闻。
3. 是否需要评论内容管理和评论审核。
4. 推荐算法是否需要加入 A/B 测试。
5. 是否需要支持多租户或多组织管理。
6. 是否需要导出统计报表。
7. 是否需要接入真实大模型 API 进行摘要和分类。
8. 是否需要部署到服务器并支持公网访问。
