# 智能传媒内容分析与推荐系统 — 系统技术方案

> 版本：V1.0 | 编制：王淦 | 日期：2026-05-29

---

## 一、方案概述

### 1.1 项目定位

面向新闻、图文、视频等融媒体内容平台，构建一个 **前后端分离** 的智能内容分析与推荐系统。重点解决三个核心问题：**内容智能化分析**、**用户兴趣建模**、**个性化内容推荐**，同时提供完整的后台管理与数据看板能力。

### 1.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **分层解耦** | 后端 API→Service→Algorithm 三层分离，前端 Views→API→Store 三层分离 |
| **渐进增强** | 算法优先用规则+轻量模型实现可运行闭环，保留 LLM/深度学习扩展接口 |
| **真实可用** | 管理员后台、权限校验、操作日志均为真实功能，非静态展示 |
| **实训友好** | 数据库/虚拟环境/依赖全部放在项目目录内，一键初始化，即装即用 |

### 2.3 选型对比分析

#### 后端框架: FastAPI vs Flask vs Django

| 维度 | FastAPI | Flask | Django |
|------|---------|-------|--------|
| 异步支持 | 原生 async/await | 需扩展 | 需 Channels |
| API 文档 | 自动生成 Swagger | 需插件 | 需 DRF |
| 类型校验 | Pydantic 原生 | 手动 | DRF Serializer |
| 学习曲线 | 低 | 低 | 高（全栈框架） |
| 适合场景 | **API 服务** | 小型项目 | 大型全栈 |

> **选型结论:** 本项目定位为 RESTful API 服务，不涉及服务端渲染，FastAPI 的异步性能 + 自动文档生成 + Pydantic 类型安全最适合。

#### 数据库: SQLite vs MySQL vs PostgreSQL

| 维度 | SQLite | MySQL | PostgreSQL |
|------|--------|-------|------------|
| 部署复杂度 | 零配置，文件即数据库 | 需独立安装服务 | 需独立安装服务 |
| 并发能力 | 读并发，写串行 | 高并发 | 高并发 |
| JSON 支持 | 基础 | JSON 列 | JSONB + 索引 |
| 适合场景 | **开发/实训/单机** | 生产环境 | 复杂查询 |

> **选型结论:** 实训阶段选择 SQLite，代码层面通过 `DATABASE_URL` 环境变量隔离，切换数据库仅改一行配置。

### 2.4 为什么不选的方案

| 未选方案 | 原因 |
|----------|------|
| **深度学习推荐模型** (TensorFlow/PyTorch) | 实训周期短，规则+轻量模型已能实现完整闭环；保留扩展接口 |
| **Elasticsearch 搜索引擎** | 运维成本高，SQL LIKE 搜索满足当前阶段需求 |
| **Redis 缓存层** | 数据量小，SQLite 直读性能足够，后续可按需引入 |
| **Docker 容器化** | 实训环境限制，脚本化部署更直接 |
| **TypeScript 前端** | 实训团队技术栈以 JS 为主，降低入门成本 |

#### 行为→画像→推荐 实时链路

```text
用户操作 (点赞某内容)
  │  POST /api/behaviors { user_id:1, content_id:42, action_type:"like" }
  ▼
behavior_service.create_behavior()
  ├─ ① 写入 user_behaviors 表
  ├─ ② _update_content_stats(content, "like")
  │      ├─ content.like_count += 1
  │      ├─ content.heat_score = calculate_heat_score(...)
  │      └─ content.quality_score = calculate_quality_score(content)
  ├─ ③ refresh_user_profile_from_behaviors(db, user_id)
  │      ├─ 遍历所有行为 → 聚合标签权重 (like 标签 +5)
  │      ├─ user.interests = "科技,AI,算法" (Top-12)
  │      ├─ user.profile_vector = "{...}" (完整画像 JSON)
  │      ├─ user.active_score += 5
  │      └─ user.last_active_at = now()
  └─ ④ db.commit()  ← 一次提交，atomic

下次推荐请求:
  recommender.recommend_for_user(user_id=1)
    ├─ 读取 user.interests → 兴趣标签权重
    ├─ 读取 user_behaviors → viewed_ids + negative_tags
    ├─ 候选打分: tag_match × 0.52 × penalty
    └─ 推荐科技类内容 ↑↑ (因为用户刚点赞了科技内容)
```

## 四、关键架构决策

### 4.1 决策记录

| # | 决策 | 方案 | 理由 |
|---|------|------|------|
| AD-1 | 算法层与业务层分离 | `algorithms/` 目录独立，纯函数设计 | 算法可独立测试、替换；后续升级 LLM 不改动业务层 |
| AD-2 | 行为记录触发连锁更新 | 同步事务内完成 content + profile 更新 | 保证数据一致性；数据量小，同步足够 |
| AD-3 | 画像双存储 | `interests`(Top-12标签) + `profile_vector`(JSON完整画像) | interests 用于推荐快速查询，profile_vector 用于画像页面展示和冷启动回退 |
| AD-4 | 推荐候选池限制 | 个性化推荐取 Top 500 候选内容 | 平衡推荐效果与计算性能；小数据量下 500 已覆盖大部分内容 |
| AD-5 | 分类多样性硬限制 | 每分类最多 `max(2, limit/3)` 条 | 避免推荐列表单一化，提升用户体验 |
| AD-6 | JWT Token 7天过期 | `ACCESS_TOKEN_EXPIRE_MINUTES=10080` | 实训场景不频繁登录，又可防止 Token 永久有效 |
| AD-7 | 敏感词自动触发审核 | 检测到敏感词 → 自动改 `status=pending` | 安全兜底，即使编辑忘记提交审核也能自动拦截 |
| AD-8 | 全项目内依赖部署 | Python 虚拟环境 + node_modules + 数据库均放在项目内 | 实训环境隔离，避免污染系统环境，支持移动和拷贝 |

### 4.2 扩展预留

| 扩展方向 | 当前实现 | 预留机制 |
|----------|----------|----------|
| SQLite → MySQL/PostgreSQL | SQLAlchemy Base + engine | 修改 `DATABASE_URL` 环境变量 |
| AI 分析升级 LLM | 规则词典 | `algorithms/` 新增 llm_analyzer.py，业务层无感切换 |
| 推荐升级深度学习 | 规则+权重 | `algorithms/` 新增 dl_recommender.py，保持相同接口签名 |
| 引入 Redis 缓存 | 直读 SQLite | `services/` 层增加缓存装饰器，不影响调用方 |
| 全文搜索 | SQL LIKE | `content_service.list_contents()` 中替换搜索实现 |
| A/B 实验 | 单一推荐策略 | 新增 `services/ab_service.py`，路由层按实验分流 |
| 实时行为处理 | 同步写入 | 新增 Kafka 生产者 + 消费者，行为 API 改为异步 |

## 六、技术风险与应对

| 风险 | 等级 | 应对措施 |
|------|------|----------|
| jieba 分词精度有限 | 中 | 保留 LLM 扩展接口；可替换为 pkuseg 或大模型 API |
| 规则分类误判率偏高 | 中 | `classify_content` 无命中时兜底"综合"；后续可引入 TF-IDF + 分类模型 |
| SQLite 并发瓶颈 | 低 | 实训场景单用户操作，并发压力小；已预留 MySQL 切换路径 |
| RSS 源不稳定 | 低 | 多条内置源并行采集，单条失败不影响整体；保留演示数据 |
| 推荐冷启动效果差 | 中 | 新用户默认推荐热门+最新内容；注册兴趣标签提供初始信号 |
